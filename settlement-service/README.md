# settlement-service


3. 강림님의 프로젝트에서의 구현 방향
강림님 프로젝트에서는 외부 PG사 데이터를 가져오기 어려우니, 다음과 같은 방식으로 **"정합성 검증 로직"**을 보여줄 수 있습니다.

Step 1: event-bot이 이벤트를 쏠 때, 의도적으로 1,000건 중 5건 정도는 OrderCreated만 보내고 PaymentConfirmed는 안 보내게 설정합니다.

Step 2: 정산 서비스의 배치가 돌 때, "결제 완료 이벤트가 없는 주문"을 찾아내어 '미결제 오류' 상태로 분류합니다.

Step 3: 이 오류 리스트를 관리자 UI(frontend-service)에서 보여주면, 이게 바로 **"정합성 검증 기능을 갖춘 정산 시스템"**의 완벽한 포트폴리오가 됩니다.

요약: payment-service에 API를 요청하는 게 아니라, 정산 서비스가 구독해서 쌓아둔 여러 종류의 이벤트들을 서로 Join해서 아귀가 맞는지 확인하는 것입니다.

이 로직을 위해 정산 서비스의 Raw Table 설계 시 order_id를 공통 키로 잡는 것이 매우 중요하겠네요. 이 방식이 강림님이 생각하신 설계 방향과 일치하나요?



⚠️ 시점의 차이 (Eventual Consistency)
정산 서비스는 '일 단위' 혹은 '주 단위' 배치로 동작하는데, ecommerce-msa는 실시간으로 돌아갑니다.

체크 포인트: 23시 59분에 발생한 OrderCreated 이벤트가 00시 01분에 PaymentConfirmed가 되었다면, 이 주문은 어느 날짜의 정산 대상인가요? **"이벤트 발생 시각"**과 "시스템 수신 시각" 중 무엇을 기준으로 삼을지에 대한 정의가 README에 포함되면 전문가 포스가 느껴집니다.

⚠️ 데이터 보존 전략 (Retention)
Raw Event를 RDB에 계속 쌓으면 용량 문제가 생길 수 있습니다.

제언: 일정 기간(예: 3개월)이 지난 Raw 데이터는 S3 같은 저렴한 저장소로 아카이빙하거나 삭제하는 TTL(Time To Live) 전략을 기획에 추가해 보세요.




나중에 README나 면접에서 **"그럼 오류가 나면 어떻게 하나요?"**라는 질문을 받을 수 있습니다. 이때 아래와 같은 대응 단계까지 설계되어 있다고 하면 완벽합니다.

Detection (탐지): 배치 작업 중 JOIN 결과가 맞지 않는 레코드를 별도의 error_log 테이블에 기록.

Notification (알림): 관리자 UI 대시보드에 '정합성 오류 발생' 알림 노출.

Action (처리): 관리자가 원본 이벤트를 재확인한 뒤, '재처리 버튼'을 눌러 해당 주문만 다시 배치 태우기.
