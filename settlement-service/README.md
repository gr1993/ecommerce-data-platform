# settlement-service
정산 서비스는 정산과 관련된 이벤트를 처리하여 Raw 테이블에 저장하고, 배치 스케줄링을 통해 일·주·월  
단위의 정산 집계 데이터를 생성하고 관리하는 서비스이다.  
Raw 이벤트 적재는 처음에는 Kafka Connector를 활용해 빠르게 MVP를 구현하고, 이후 검증·재처리·변환  
로직이 필요할 경우 별도의 Kafka Consumer를 구현하여 보완할 계획이다.  


### Reconciliation(대조)
event-bot에서는 일부러 결함이 포함된 이벤트를 발생시키도록 구현할 예정이다.  
예를 들어, 1,000건 중 약 5건은 OrderCreated 이벤트만 발생하고 PaymentConfirmed 이벤트는  
발생하지 않도록 한다. 정산 서비스의 배치가 실행될 때, 결제나 주문 완료 이벤트가 없는 주문을 찾아  
오류 주문으로 분류한다. 이 과정에서 **결제와 주문 Raw 테이블은 order_id를 공통 키**로 사용하여  
대조에 활용할 계획이다.  
오류로 분류된 주문에 대해서는 현업에서 실제로 다음과 같은 전략 중 하나를 선택하게 된다.  

* Detection (탐지): 배치 작업 중 JOIN 결과가 맞지 않는 레코드를 별도의 error_log 테이블에 기록
* Notification (알림): 관리자 UI 대시보드에 '정합성 오류 발생' 알림 노출
* Action (처리): 관리자가 원본 이벤트를 재확인한 뒤, '재처리 버튼'을 눌러 해당 주문만 다시 배치 태우기

이번 사이드 프로젝트에서는 **탐지(Detection)와 알림(Notification) 전략**을 활용하여, 배치 작업 중  
불일치가 발생하면 error 테이블에 기록하고 관리자가 이를 확인할 수 있는 구조로 구현할 예정이다.


### 정산 전략
정산 전략에서 가장 먼저 결정해야 하는 것은 주문 시점이다. 정산 서비스는 일 단위 또는 주 단위로 동작하는  
반면, ecommerce-msa의 주문·결제 서비스는 실시간으로 운영된다.  
따라서 정산에서는 **어느 시점을 기준으로 데이터를 집계할지를 명확히 정하는 것이 매우 중요**하다.  
예를 들어, 23시 59분에 발생한 OrderCreated 이벤트가 00시 01분에 PaymentConfirmed가 되었다면,  
어느 날짜의 정산 대상에 포함시킬지 명확한 기준이 필요하다. 이번 사이드 프로젝트에서는 프로세스를 단순화하기  
위해 OrderCompleted와 같은 주문 확정 단계는 생략하고, PaymentConfirmed 이벤트의 **paidAt 필드를 기준**으로  
정산 대상을 결정할 예정이다.  

두 번째로 중요한 것은 데이터 보존 전략이다. Raw Event를 RDBMS에 계속 쌓으면 용량 문제가 발생할 수 있다.  
이를 해결하기 위해, PostgreSQL에서 지원하는 **테이블 파티셔닝을 활용**하여 하루 단위로 파티션을 구성할 예정이다.  
이렇게 구성하면 조회 시 Partition Pruning을 통해 필요한 파티션만 선택적으로 조회할 수 있어 성능상의 이점을  
얻을 수 있다. 또한, 일정 기간(예: 3개월)이 지난 Raw 데이터는 S3와 같은 저장소로 아카이빙하거나 삭제할 수  
있는 TTL(Retention) 전략을 설정할 수 있다.  
다만, 이번 사이드 프로젝트 수행 기간이 길지 않기 때문에 아카이빙이나 삭제 전략은 생략할 예정이다.
