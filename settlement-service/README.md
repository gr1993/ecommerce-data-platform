# settlement-service
정산 서비스는 정산과 관련된 이벤트를 처리하여 Raw 테이블에 저장하고, 배치 스케줄링을 통해 일·주·월  
단위의 정산 집계 데이터를 생성하고 관리하는 서비스이다.  
Raw 이벤트 적재는 초기에는 Kafka Connector를 활용하여 빠르게 구현하려 했으나, 이전 프로젝트인  
ecommerce-msa에서는 Kafka에 단순 JSON 구조의 레코드를 저장하는 방식으로 개발되었다.  
하지만 Kafka Connector는 기본적으로 스키마 정보가 포함된 레코드 처리를 전제로 하는 도구이기 때문에,  
현재 구조에서는 적합하지 않다고 판단하였다. 이에 따라 정산 서비스에서는 Kafka Consumer를 직접 구현하여  
Raw 데이터 적재 로직을 처리할 예정이다.  


### Reconciliation(대조)
event-bot에서는 일부러 결함이 포함된 이벤트를 발생시키도록 구현할 예정이다.  
예를 들어, 1,000건 중 약 5건은 OrderCreated 이벤트만 발생하고 PaymentConfirmed 이벤트는  
발생하지 않도록 한다. 정산 서비스의 배치가 실행될 때, 결제나 주문 완료 이벤트가 없는 주문을 찾아  
오류 주문으로 분류한다. 이 과정에서 **결제와 주문 Raw 테이블은 order_number를 공통 키**로 사용하여  
대조에 활용할 계획이다.  
오류로 분류된 주문에 대해서는 현업에서 실제로 다음과 같은 전략 중 하나를 선택하게 된다.  

* Detection (탐지): 배치 작업 중 JOIN 결과가 맞지 않는 레코드를 별도의 error_log 테이블에 기록
* Notification (알림): 관리자 UI 대시보드에 '정합성 오류 발생' 알림 노출
* Action (처리): 관리자가 원본 이벤트를 재확인한 뒤, '재처리 버튼'을 눌러 해당 주문만 다시 배치 태우기

이번 사이드 프로젝트에서는 **탐지(Detection)와 알림(Notification) 전략**을 활용하여, 배치 작업 중  
불일치가 발생하면 각 raw 테이블 대조 상태에 기록하고 관리자가 이를 확인할 수 있는 구조로 구현할 예정이다.  


### 정산 전략
정산 전략에서 가장 먼저 결정해야 하는 것은 주문 시점이다. 정산 서비스는 일 단위 또는 주 단위로 동작하는  
반면, ecommerce-msa의 주문·결제 서비스는 실시간으로 운영된다.  
따라서 정산에서는 **어느 시점을 기준으로 데이터를 집계할지를 명확히 정하는 것이 매우 중요**하다.  
예를 들어, 23시 59분에 발생한 OrderCreated 이벤트가 00시 01분에 PaymentConfirmed가 되었다면,  
어느 날짜의 정산 대상에 포함시킬지 명확한 기준이 필요하다. 이번 사이드 프로젝트에서는 프로세스를 단순화하기  
위해 OrderCompleted와 같은 주문 확정 단계는 생략하고, PaymentConfirmed 이벤트의 **paidAt 필드를 기준**으로  
정산 대상을 결정할 예정이다.  

두 번째로 중요한 것은 데이터 보존 전략이다. Raw Event를 RDBMS에 계속 쌓으면 용량 문제가 발생할 수 있다.  
이를 해결하기 위해, PostgreSQL에서 지원하는 **테이블 파티셔닝을 활용**하여 하루 단위로 파티션을 구성할 예정이다.  
이렇게 구성하면 조회 시 Partition Pruning을 통해 필요한 파티션만 선택적으로 조회할 수 있어 성능상의 이점을  
얻을 수 있다. 또한, 일정 기간(예: 3개월)이 지난 Raw 데이터는 S3와 같은 저장소로 아카이빙하거나 삭제할 수  
있는 TTL(Retention) 전략을 설정할 수 있다.  
다만, 이번 사이드 프로젝트 수행 기간이 길지 않기 때문에 아카이빙이나 삭제 전략은 생략할 예정이다.  

* [파티셔닝 정리 블로그](https://little-pecorino-c28.notion.site/31b82094ef0a8021bed7fb23995d8cc5)
* 파티션 테이블 생성은 현업에서는 pg_partman과 같은 자동화 도구를 사용하거나, 스케줄러 기반으로 자동 생성하는 방식을 주로 활용한다.
다만, 이번 사이드 프로젝트에서는 필요한 시점에 PartitionManagementServiceTest에 정의한 테스트 함수를 실행하여 파티션을 생성하는 방식을 사용할 예정이다.


### 정산 배치 주기
정산 배치는 Daily 배치를 기본으로 구성하며, 사용자 트래픽이 적은 시간대인 02:00에 매일 실행되는  
것으로 가정한다. 주간 및 월간 정산 데이터는 Daily 정산 결과를 집계하여 산출하도록 구현할 예정이다.  
이는 Daily 단위에서 이미 계산이 완료된 데이터를 단순 합산하는 방식이므로 시스템 부하가 적고, 검증이  
용이하다는 장점이 있다.  
정산 배치에서 고려해야 할 중요한 사항 중 하나는 예외 케이스 처리이다. 예를 들어, 카프카 브로커 장애로  
인해 이벤트 처리가 지연되거나, 결제 대행사(PG)로부터 결제 성공 통보가 늦게 도착하는 경우, 실제 결제  
시점과 이벤트 수신 시점 간의 불일치가 발생할 수 있다. 이로 인해 이전에 발생한 결제임에도 불구하고 다음  
날 데이터로 유입되는 상황이 생길 수 있다.  
이러한 문제를 해결하기 위해 raw 테이블에 정산 처리 여부를 나타내는 is_reconciled 플래그를 추가하여 관리한다.  
배치 실행 시에는 paidAt < 오늘 00시 AND is_reconciled = 'N' 조건으로 조회하여, 장애나 지연으로 인해  
처리되지 못한 과거 데이터까지 함께 포함되도록 한다.  
또한 시스템 장애는 일반적으로 며칠 내 복구되는 점을 고려하여, 약 7일 정도의 조회 윈도우를 설정할 예정이다.  
Daily 배치는 이 기간을 기준으로 미처 반영되지 않은 정산 데이터를 보완하는 방식으로 동작한다.  
성능 최적화를 위해 is_reconciled = 'N' 조건을 기준으로 부분 인덱스를 구성하고, 해당 구간에서 paidAt 범위를  
추가로 탐색하도록 한다. 이를 통해 이미 정산이 완료된 수억 건의 데이터('Y')는 인덱스에서 제외되고, 실제  
조회 대상은 미정산 상태의 수천~수만 건 수준으로 크게 줄어들어 검색 성능을 향상시킬 수 있다.

### Spring Batch
정산 데이터는 하루 수십만 건 이상 쌓이는 대용량 데이터이다. Spring Batch를 활용하면 Chunk 지향  
처리 방식을 통해 메모리 효율성을 높이고 트랜잭션 관리를 최적화할 수 있어 적합한 선택이다.  
또한 배치 실행 이력, 성공/실패 여부, 처리 건수 등이 DB에 자동으로 기록되며, 처리 중 특정 지점에서  
오류가 발생하더라도 해당 지점부터 재시작하거나 일부 구간을 건너뛸 수 있는 기능을 기본적으로 제공한다.  


### 재처리 시뮬레이션
배치 처리 과정 중 일부로, 3월 2일 정산 데이터를 처리할 때 의도적으로 오류가 발생하도록 코드를 추가하였다.  
그 상태로 실행한 결과, 모든 파티션은 두 번째 단계인 dailySalesWorkerStep까지 수행되었으며, 이 중  
3월 2일에 해당하는 dailySalesWorkerStep:partition-2026-03-02만 실패로 처리되었다.  
이로 인해 3월 2일 Step의 실패가 전체 흐름에 영향을 주었고, 이미 성공한 다른 날짜의 파티션들도 다음 단계인  
dailyCancelWorkerStep으로 진행하지 못한 채 Job이 종료되었다. 이를 통해 파티셔닝 Job에서는 각 Step에  
포함된 모든 파티션이 성공해야만 다음 Step으로 넘어간다는 것을 확인할 수 있었다.  
또한 각 파티션 Step의 실행 이력은 Spring Batch 에 의해 개별적으로 관리된다. 따라서 재실행 시(이전 실행과  
동일한 Job 파라미터를 사용하는 경우), 실패했던 dailySalesWorkerStep:partition-2026-03-02만 다시  
실행되었고, 해당 Step이 성공하면 이후 단계부터는 모든 파티션이 정상적으로 이어서 수행되어 최종적으로 Job이  
완료되었다.  
결과적으로 파티셔닝 방식에서는 Step 단위의 실행 상태를 프레임워크가 관리해주기 때문에 별도의 재처리 로직을  
구현할 필요가 없다. 반면, taskExecutor를 활용하여 Step 내부에서 Chunk 단위 병렬 처리를 수행하는 경우에는  
saveState 옵션을 true로 설정하거나, 재처리를 위한 별도의 상태 정보를 직접 저장하고 관리해야 한다.
